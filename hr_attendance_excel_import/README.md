# Excel Attendance Import — Odoo 18

موديول مستقل لاستيراد الحضور من XLSX إلى `hr.attendance`، مع معاينة، اختيار الصفوف، مراجعة التوقيت والتعارضات، وسجل دائم. لا يغيّر ملفات Odoo الأساسية ولا ينشئ موظفين أو إجازات.

## نتيجة فحص المشروع وحدود التحقق

- `docker-compose.yml` يستخدم `odoo:18.0` وPostgreSQL 15. مسار `/mnt/extra-addons` موجود في `config/odoo.conf` ومربوط بمجلد الإضافات المحلي؛ مكان الموديول مناسب للإعدادات الحالية.
- لم تظهر امتدادات مباشرة لـ `hr.employee` أو `hr.attendance` في إضافات المشروع المحلية وقت الفحص. ده مش تأكيد لحالة الإضافات المثبتة أو تعديلات Studio داخل قاعدة البيانات.
- تمت مراجعة نسخة سورس Odoo 18 المحلية: حقلا `barcode` و`identification_id` موجودان، وقيود الحضور تمنع تداخل الفترات وتعدد سجلات الحضور المفتوحة. لم يتم تحديد أي حقل منهما كافتراض لكود الموظف.
- الوصول إلى Docker لم يُسمح به. لم تُفحص قاعدة البيانات أو الشركات أو حقول الموظفين الفعلية، ولم يُجرَ تثبيت أو اختبار تكامل داخل Odoo. يلزم اختبار على قاعدة تجريبية قبل التشغيل الفعلي.

## التثبيت

**ده موديول Python على السيرفر، وليس Data Module قابلًا للرفع من زر Import Module بصيغة ZIP.** اترك مجلده داخل `addons_path`، وأعد تشغيل Odoo، ثم استخدم Update Apps List وInstall/Upgrade.

1. المجلد `hr_attendance_excel_import` موجود بالفعل داخل `extra-addons`.
2. تأكد أن `openpyxl` متاح لنفس Python اللي بيشغّل Odoo. المكتبة موجودة في requirements الرسمية لـ Odoo 18، لكن تحقق من صورة التشغيل الفعلية:

   ```bash
   docker compose exec web18_test python3 -c "import openpyxl; print(openpyxl.__version__)"
   ```

   لو مش موجودة، ضمّن `python3-openpyxl` أو `openpyxl` في صورة Docker المخصصة وأعد بناءها؛ التثبيت المؤقت داخل حاوية مش حل دائم. ملف Compose الحالي يستخدم `image: odoo:18.0` ولا يستخدم Dockerfile المحلي تلقائيًا.
3. أعد تشغيل خدمة Odoo، ثم فعّل وضع المطور، وافتح Apps → Update Apps List.
4. ابحث عن **Excel Attendance Import** مع إزالة فلتر Apps لو لزم، وثبّته أولًا على قاعدة تجريبية.
5. امنح المستخدم صلاحية **Attendances / Administrator** وصلاحيات قراءة الموظفين المطلوبة. حقول الهوية والبادج قد تحتاج **Employees / Officer** حسب صلاحيات Odoo الحالية؛ الموديول لا يتجاوز صلاحيات الحقول.

لا توجد تغييرات مطلوبة على `config/odoo.conf` أو `docker-compose.yml` للمسار الحالي، ولم يتم تعديلهما.

## تشخيص خطأ serialization_guard وإصلاح إعادة التحميل — 18.0.1.0.1

تمت مراجعة ملفات الموديول وسورس Odoo 18 المحلي. سلسلة التسجيل سليمة:
`__init__.py → models/__init__.py → attendance_import.py → ImportLock`.
الموديل `hr.attendance.excel.import.lock` موجود، وحقل `revision` له default يساوي صفر وليس حقلًا إجباريًا ناقصًا. تعريف XML الفارغ صحيح. الاعتماد `hr_attendance` مسجل، و`openpyxl` معلنة كاعتماد Python. تحميل ACL بعد ملف security ليس سببًا للفشل في التثبيت القياسي، لأن تحميل بيانات الموديول يتم بصلاحية النظام وبعد تسجيل موديلات Python.

اللوج المتاح وقت المراجعة يحتوي على تحميل ناجح سابق للموديول على قاعدة `test` بتاريخ 2026-10-18 الساعة 10:38:52، بما فيه `security/security.xml`، ثم فتح معالج الاستيراد. لا يحتوي اللوج على traceback للمحاولة الفاشلة المذكورة، وبالتالي لا يمكن تأكيد الاستثناء الداخلي لتلك المحاولة من اللوج الحالي وحده.

صيغة `Error while importing module ...` موجودة في `_import_zipfile` داخل `base_import_module` في Odoo 18. هذا المسار يستخرج XML/CSV والملفات الثابتة والترجمات، ولا يحمّل ملفات Python الخاصة بالموديول. إذا استُخدم قبل تثبيت الموديول على السيرفر، فلن يوجد موديل القفل في registry، وسيقف قارئ XML عند أول `env[rec_model]`. لذلك استخدام Import Module ZIP هو التفسير المدعوم لمسار الخطأ، والحل نشر الموديول على السيرفر وتثبيته بالطريقة القياسية؛ حذف القفل أو تبديل ترتيب ACL لن يحمّل موديلات Python المفقودة.

وجدت المراجعة أيضًا حالة مستقلة عند إعادة تحميل XML بوضع `init` بعد وجود السجل: Odoo يستدعي `_load_records_write({})`، والذي يستدعي `write({})` افتراضيًا؛ حارس الموديول كان يرفضها حتى لو لا يوجد أي تغيير. الإصلاح يسمح بإعادة إعلان XML الفارغة فقط من خلال hook خاص `_load_records_write`، من غير كتابة أو تصفير `revision`. أي قيم غير فارغة تظل خاضعة لحماية الكتابة المعتادة. التحديث القياسي بوضع `update` يحافظ على `noupdate="1"`، فلا يغيّر السجل أصلًا.

لم يُحذف `serialization_guard` ولم تتغير هويته أو الموديل أو الجدول أو منطق `SELECT ... FOR UPDATE` وتحديث `revision`. لم يتم فتح `sudo()` أو السماح بتغيير الحارس عبر RPC أو عبر مجرد context مثل `install_mode=True`. أضيفت 3 اختبارات Odoo: إعادة تحميل XML بوضع init/update مع حفظ هوية السجل والعداد، رفض التعديل العام، والتأكد أن القفل يمنع معاملة قاعدة بيانات أخرى من الحصول عليه بـ NOWAIT.

تم أيضًا إضافة `role="status"` لرسالة المعاينة لمعالجة تحذير XML ظاهر في اللوج؛ التحذير لم يكن سبب فشل التثبيت.

### تطبيق الإصلاح والتحقق

1. تأكد أن مجلد الموديول الحالي هو الموجود داخل `/mnt/extra-addons` في الحاوية، وأن `openpyxl` متاحة.
2. أعد تشغيل خدمة Odoo لتحميل تعديل Python:

   ```bash
   docker compose restart web18_test
   ```

3. فعّل وضع المطور، ثم Apps → Update Apps List. استخدم **Install** لو غير مثبت، أو **Upgrade** لو مثبت. لا ترفع ZIP من Import Module. اللوج الحالي يدل على تحميل سابق للموديول على قاعدة `test`، فلا تفترض أنه غير مثبت.
4. على قاعدة اختبار منفصلة، نفّذ التثبيت ثم التحديث؛ استبدل `ATTENDANCE_TEST_DB` باسم قاعدة تجريبية مخصصة:

   ```bash
   docker compose exec web18_test odoo -c /etc/odoo/odoo.conf \
     -d ATTENDANCE_TEST_DB -i hr_attendance_excel_import --without-demo=all \
     --test-enable --test-tags /hr_attendance_excel_import \
     --stop-after-init --no-http --logfile=/tmp/attendance-install-tests.log

   docker compose exec web18_test odoo -c /etc/odoo/odoo.conf \
     -d ATTENDANCE_TEST_DB -u hr_attendance_excel_import \
     --test-enable --test-tags /hr_attendance_excel_import \
     --stop-after-init --no-http --logfile=/tmp/attendance-upgrade-tests.log
   ```

5. راجع اللوجين داخل الحاوية: نجاح تحميل الموديول، وعدم وجود ERROR/FAIL في اختبارات الموديول. الاختبارات تشمل إنشاء الحضور، إعادة رفع نفس الملف بدون تكرار، التداخل، تحديث الانصراف، وثلاثة اختبارات الحارس المذكورة.
6. من الواجهة، استورد ملفًا صغيرًا لموظف تجريبي بعد المعاينة. تحقق من سجل `hr.attendance` والدخول والخروج، ثم ارفع نفس الملف ثانية بسياسة Skip Existing: يجب أن يكون Duplicate ولا يزيد عدد سجلات الحضور. افتح معاينتين لنفس الملف قبل التنفيذ؛ بعد تنفيذ الأولى، الثانية يجب أن تعيد الفحص وتتخطى السجل الموجود.

أُعيد تشغيل اختبارات المحلل المستقلة بنجاح بعد الإصلاح. لم تُشغّل أوامر Docker أو اختبارات Odoo الجديدة لأن الوصول إلى Docker لم يُسمح به في جلسة المراجعة. نجاح التحميل في اللوج السابق دليل سابق، وليس نتيجة اختبار النسخة المعدلة.

## التشغيل

من الإصدار `18.0.1.0.2`، تقرير الأخطاء يعرض أعمدة المصدر بنفس عناوينها وترتيبها في الشيت المختار، بدل `Original column 1` وهكذا. تظل أعمدة Row وEmployee code وStatus وReason في بداية التقرير. العناوين تُقرأ من الملف المحفوظ مع العملية، لذلك يمكن إعادة تنزيل تقارير العمليات السابقة بالأسماء الأصلية بعد التحديث، دون إعادة استيراد الحضور.

المكان: **Attendances → Configuration → Import Attendances**.

1. ارفع ملف `.xlsx` واختار الشركة. الاستيراد الواحد خاص بشركة واحدة من الشركات المفعّلة والمسموحة للمستخدم.
2. اختار **Employee Code Field** يدويًا: لازم يكون حقل نصي مخزّن ومقروء على `hr.employee`، وغير معتمد على الشركة كـ property field. السيرفر يتحقق من الاختيار حتى لو تم استدعاء المعالج عبر RPC.
3. اختار **Timezone**. الافتراضي من تقويم شركة المستخدم الحالية، أو توقيت المستخدم إن لم يتوفر. راجع الاختيار صراحةً، خصوصًا لو غيّرت الشركة في المعالج.
4. الشاشة تعرض أسماء الشيتات مرقمة؛ أدخل رقم الشيت المطلوب في **Worksheet Number**. أول شيت رقمه 1.
5. اضبط السياسات والحدود، واضغط **Validate and Preview**. المرحلة دي تحفظ المعاينة فقط ولا تنشئ حضورًا.
6. راجع Employee Name والأوقات والحالة والسبب. يمكنك إلغاء تحديد **Approved** للصفوف الصالحة التي لا تريد استيرادها.
7. اضغط **Confirm Import**. يعاد فحص الملف والمطابقة والتعارضات قبل التنفيذ. تغيّر الموظف أو السجل المستهدف أو قيمة الانصراف السابقة منذ المعاينة يمنع تنفيذ الصف.
8. استخدم **Download Error Report** لتنزيل الصفوف غير المستوردة وأسبابها والأعمدة الأصلية، أو افتح **Import History** للمراجعة لاحقًا.

زر **Validate Again** يعيد بناء المعاينة ويعيد اختيار الصفوف؛ لا تحتفظ هذه العملية بإلغاء الاختيار السابق. لا يمكن تعديل ملف أو إعدادات سجل الاستيراد؛ أنشئ معاينة جديدة لتغيير الإعدادات. العملية المكتملة لا تُنفذ مرة أخرى.

## شكل Excel

أول صف لازم يحتوي العناوين؛ ترتيب الأعمدة قابل للتغيير. الأعمدة المطلوبة:

| المعنى | العناوين المدعومة |
|---|---|
| كود الموظف | `كود الموظف`, `Employee Code`, `Code` |
| التاريخ | `التاريخ`, `Attendance Date`, `Date` |
| الدخول | `الحضور`, `Check In`, `Check-In`, `check_in` |
| الخروج | `الانصراف`, `انصراف`, `Check Out`, `Check-Out`, `check_out` |
| الشيفت — اختياري | `الشيفت`, `Shift` |

الأعمدة الإضافية محفوظة في بيانات الصف الأصلية للمراجعة ولا تؤثر على حساب الحضور. يتم تجاهل الصفوف الفارغة بالكامل. العناوين الإنجليزية غير حساسة لحالة الحروف والمسافات الخارجية يتم حذفها.

- التاريخ: Excel date أو نص ISO مثل `2026-09-02`.
- الوقت: Excel time أو datetime (يُستخدم جزء الوقت مع عمود التاريخ)، كسر يوم بين 0 و1، أو `HH:MM` / `HH:MM:SS`.
- الكود نصي ويحافظ على الأصفار البادئة؛ الرقم بتنسيق Excel مثل `00000` يحافظ على العرض `00012`. الأكواد الطويلة 15 رقمًا أو أكثر والأكواد غير الصحيحة عدديًا لازم تُخزن كنص لتفادي فقد الدقة.
- لا تقييم للمعادلات: أي صف فيه formula يتم رفضه حتى في عمود إضافي. لا تُستخدم النتائج المحفوظة كبديل صامت.
- الصيغ الأخرى مثل `.xls` و`.csv` غير مدعومة.

## مطابقة الموظفين

بحث مجمّع باستخدام الكود والحقل المحدد داخل الشركة المختارة. الموظفون المؤرشفون يدخلون في فحص التفرد أيضًا؛ لا يتم إخفاء ازدواج الكود بسبب الأرشفة. يلزم نتيجة واحدة بالضبط؛ لا توجد مطابقة بالاسم أو إنشاء موظفين تلقائيًا. الحقل `barcode` ليس افتراضيًا. تكرار الكود داخل الشركة ينتج `Ambiguous Employee`، وعدم وجوده ينتج `Missing Employee`.

## التوقيت والورديات الليلية

التوقيت في المصدر يفسّر داخل المنطقة الزمنية المختارة باستخدام `zoneinfo` ثم يتحول إلى UTC بدون offset ثابت. الأوقات المبهمة أو غير الموجودة عند تغيير التوقيت الصيفي تُرفض للمراجعة. أوقات المعاينة من نوع Odoo Datetime، ولذلك تُعرض حسب timezone المستخدم في Odoo، وليس بالضرورة timezone المصدر.

لو الانصراف أسبق من الحضور، يُضاف يوم للانصراف، ثم تُراجع المدة الفعلية بعد التحويل إلى UTC. مثال `13:48:22 → 00:05:44` يُعامل كورديّة لليوم التالي. الرسالة `Overnight shift` معلومة، مش خطأ. تساوي الدخول والخروج مرفوض. المدة الافتراضية القصوى 16 ساعة، ويمكن ضبطها حتى 48 ساعة؛ صيغة الملف ذات الوقت فقط تدعم عبور منتصف الليل مرة واحدة.

## السياسات

**البصمات الناقصة:**

- **Strict** الافتراضي: يرفض الصف الناقص.
- **Allow Open Attendance**: يسمح بدخول بلا خروج لو مفيش تعارض. لا يُنشئ دخولًا افتراضيًا لخروج منفرد.
- **Skip Incomplete**: يتخطى الصف الناقص مع السبب.
- نصوص الإجازة المعروفة مثل `إجازة` و`اجازة` و`Leave` تتخطى الصف بالكامل. النصوص غير المعروفة تُرفض كوقت غير صالح؛ لا توجد معالجة إجازات HR تلقائية.

**التكرار:**

- المطابقة بالموظف والدخول والخروج، وليس الموظف واليوم فقط؛ الجلسات المنفصلة في نفس اليوم مسموحة. نهاية جلسة تساوي بداية الجلسة التالية مسموحة.
- **Skip Existing** يتخطى السجل المطابق تمامًا. نفس الدخول مع خروج مختلف يعتبر تعارضًا، ولا يُتخطى باعتباره مطابقًا.
- **Report Conflicts** يعتبر السجل المطابق الموجود خطأ للمراجعة.
- **Update Existing** يحتاج سجلًا واحدًا بنفس الموظف والدخول، ويغيّر الخروج فقط بعد التحقق من عدم التداخل. لا يمسح خروجًا موجودًا لإعادة فتح جلسة.
- السجل غير المنشأ بالموديول يحتاج تحديد مربع الموافقة الصريح قبل المعاينة. يشمل ذلك السجلات اليدوية وسجلات الكشك وأي مصدر آخر. المعاينة والسجل النهائي يحتفظان بالانصراف السابق؛ تحديثات الحضور تمر أيضًا عبر ORM المعتاد.
- تكرار الصف داخل الملف يُتخطى. التداخل داخل الملف أو مع حضور موجود يُرفض، بما في ذلك الحضور المفتوح.

## الأمان والتزامن والأداء

كل العمليات لمدير الحضور فقط، مع ACL وقواعد شركات على الملف والسجل والصفوف. لا يوجد `sudo()` ولا إدخال حضور بـ SQL. المعاينة قابلة لتغيير اختيار الصف فقط؛ النتائج وملكية المصدر لا يمكن تزويرها بتعديل الحقول عبر RPC. سجلات التدقيق غير قابلة للحذف من واجهة المستخدم.

يستخدم التنفيذ savepoint لكل صف؛ أخطاء قيود Odoo المتوقعة تُسجل وتسمح بإكمال بقية الصفوف. الأخطاء غير المتوقعة وأخطاء الصلاحيات تنتشر للخارج وتعيد المعاملة بالكامل بدل إخفائها. توجد إعادة تحقق قبل التنفيذ، وتسلسل لعمليات هذا المستورد بقفل قاعدة البيانات وتحديث سجل حارس عن طريق ORM؛ المعاملات ذات snapshot قديم تُترك لآلية إعادة المحاولة القياسية في Odoo.

**حد التزامن:** القفل ينسّق العمليات الصادرة من هذا الموديول. الكشك أو API خارجي لا يستخدم الحارس؛ لا يوجد ضمان أقوى من قيود Odoo القياسية أمام كتابة متزامنة من مصدر خارجي. نفّذ الاستيراد التاريخي في نافذة مناسبة واختبر مسارات الحضور الخارجية قبل التشغيل الإنتاجي.

المطابقة وقراءة الحضور مجمعتان، وفحص الفترات يستخدم فهارس مرتبة في الذاكرة. الإنشاء عبر ORM لكل صف للحفاظ على savepoints والقيود وسجل الخطأ. مدة التنفيذ داخل Odoo تتأثر بحسابات الوقت الإضافي والإضافات الأخرى. لم يُقَس أداء ORM على قاعدة فعلية.

الحدود الافتراضية: 10 MB و10000 صف و100 عمود. يمكن ضبط الملف حتى 50 MB والصفوف حتى 50000، مع حد إضافي لحجم ZIP بعد فك الضغط (20 ضعف حد حجم الملف) وعدد أجزائه (1000). هذه حدود أمان وليست وعدًا بزمن تنفيذ؛ اضبط حدود الرفع والذاكرة ووقت طلب Odoo حسب بيئة التشغيل.

## الاختبارات ونتائج التحقق

اختبارات المحلل المستقلة:

```bash
PYTHONPATH=/tmp/attendance-import-deps python3 extra-addons/hr_attendance_excel_import/tests/test_parser.py
```

المسار `/tmp/attendance-import-deps` خاص ببيئة التطوير الحالية حيث تم تثبيت `openpyxl` مؤقتًا؛ في بيئة تحتوي المكتبة يمكن تشغيل الأمر بدون `PYTHONPATH`.

تم تنفيذ **24 اختبارًا ونجحت كلها**: صيغ التاريخ والوقت، Cairo UTC، الورديات الليلية، DST المبهم/المفقود، البصمات الناقصة، الإجازات، الأوقات غير الصالحة، الحدود، العناوين العربية والإنجليزية، المعادلات، الأصفار البادئة، الشيتات والتداخل. تم فحص syntax لملفات Python وXML أيضًا.

تجربة إضافية على 5000 صف مُنشأ للاختبار انتهت قراءة وفحص أوقاتها في حوالي 0.65 ثانية على بيئة التطوير. الرقم خاص بالمحلل فقط، ولا يقيس ORM أو حسابات Odoo أو زمن رفع الملف.

تجربة الملف المقدم، بافتراض `Africa/Cairo` وStrict و16 ساعة، دون مطابقة موظفين أو كتابة قاعدة بيانات: **28 صفًا: 21 صالحًا زمنيًا، 5 بصمات ناقصة، وصفان إجازة تم تخطيهما**. دي ليست نتيجة استيراد فعلي أو تأكيد صلاحية الموظفين.

اختبارات Odoo المكتوبة تغطي الاستيراد والمطابقة والموظف المجهول والكود المكرر وإعادة الاستيراد والتكرار والتداخل وجلسات نفس اليوم والبصمات والإجازة والتوقيت والشركات والصلاحيات والتحديث وموافقة السجلات اليدوية والملفات غير الصالحة وحماية المعاينة وإعادة التحقق. **لم تُنفذ اختبارات Odoo ولم يتم تأكيد نجاح التثبيت** لعدم توفر وصول Docker وعدم توفر runtime Odoo/PostgreSQL كامل محليًا.

لتشغيلها على قاعدة تجريبية منفصلة، استبدل `ATTENDANCE_TEST_DB` باسم قاعدة الاختبار، وليس قاعدة الإنتاج:

```bash
docker compose exec web18_test odoo -c /etc/odoo/odoo.conf \
  -d ATTENDANCE_TEST_DB -i hr_attendance_excel_import \
  --test-enable --test-tags /hr_attendance_excel_import \
  --stop-after-init --http-port=8079 --logfile=/tmp/attendance-import-tests.log
```

راجع ملف اللوج داخل الحاوية، وثبّت الموديول واختبر المعاينة والاستيراد الفعلي على نسخة بيانات آمنة قبل الإنتاج. لا يشغّل الأمر تلقائيًا أي إجراء على قاعدة المشروع الحالية.
